## P1 — RTK：迟到错误不能只剩代理错误

[v1.2.1](https://github.com/rtk-ai/rtk/releases/tag/v1.2.1) 页面显示 11 月 19 日，包含代理请求超时、Windows 代理恢复和 .NET 测试项目计数修复。后者改为计数不同项目，而非路径在输出中出现的次数；摘要统计仍需有可回溯的原始依据。

[请求预算修复](https://github.com/rtk-ai/rtk/commit/6fc6d281d265bd87f745a4964a104cee2d6b458a) 说明旧逻辑按每次尝试计时，并把静默超时再次重发；修复让尝试共享 deadline，只有连接失败重试。[后续迟到错误修复](https://github.com/rtk-ai/rtk/commit/638d99888f2eb5c67ff4e145bbdf03258b0f6620) 又调整错误体的读取预算起点，避免流式请求收到较晚错误后立刻耗尽预算、最终只呈现通用 502。不能把前一个提交的描述当作整个发行版最后的错误处理语义，也不据此声称成功的 SSE 流均被同一总时限截断。

对 [[AxisAgent]] 的推论：保留连接尝试、已知上游状态、错误体是否读全及代理超时原因；请求已发出后的沉默不等同于未执行。今天将该证据加入 [[Agent Verification and Audit Plane]]，本轮未接入代理或更改重试配置。

### 压缩收益的测量口径

[RTK 当前 README](https://github.com/rtk-ai/rtk) 将命令输出压缩与可选 API proxy 分开，并明确输出压缩比例不等于总账单节省比例；token 统计采用 bytes/4 估算。其关于原始输出回退、退出码传递及完整输出入口的承诺是项目声明，本轮未验证。

Windows/.NET 借鉴：消费压缩日志时仍保留命令身份、退出码、完整日志位置与统计口径；不能把更短的摘要直接视为检查更充分，也不能将估算 token 写成 provider 的实际计费记录。

Windows/.NET 借鉴：应用版本、UI 框架版本、引擎制品和模型用途分别记录；OCR、ASR、翻译共享模型格式不代表能力可互换。人工修改的文件、源图与译文行对应关系需保留来源。本轮未打开媒体、下载模型或执行 .NET 构建测试。
