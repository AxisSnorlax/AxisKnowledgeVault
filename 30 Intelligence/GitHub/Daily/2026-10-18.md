### P1 — Konnect：先确认写入结果，再决定能否重试

官方资料描述通过 KiCad IPC 编辑 PCB、接入原生撤销/重做，并通过 KiCad CLI 检查和导出。不同编辑路径不能被当成等价的状态来源。[README](https://github.com/mixelpixx/Konnect)。

本次复核的 [v0.13.0](https://github.com/mixelpixx/Konnect/releases/tag/v0.13.0) 发布页显示日期为 10 月 2 日，并非今天的新发布。它明确区分现场 IPC、保存文件与 CLI 证据；操作可能已越过写入边界时，要求先检查当前状态，避免直接重复写入。

对 AFSCADA / AxisProtocolStudio 的设计推论：超时不等于没有执行。结果需要标出目标文档/设备、证据来源和写入是否确定，重试资格由业务合同决定。该增量加入 [[Professional Software Agent Surface]]。制造文件与电气检查仍需领域验收，本轮未操作 KiCad 或硬件。

### P1 — winapp CLI：查询项目实际引用的 API

微软仓库把 SDK、应用身份、MSIX 打包和开发工具统一为 CLI，并覆盖多种应用框架。[仓库](https://github.com/microsoft/winappCli)。

当前 main 分支的 [find-api 文档](https://github.com/microsoft/winappCli/blob/main/docs/usage.md#find-api) 描述从项目已解析的元数据回答类型/成员问题，并区分项目与 SDK 范围；索引不完整时对否定结果加以说明。成员存在也不等于可赋值，调用者仍须检查返回信息。

对 Windows/.NET Agent 的借鉴：生成 C#/XAML 前先核对目标项目、包版本与索引完整性，不拿机器上更新的 Runtime 充当项目编译依据。读取到的 [v0.7.1 发布页](https://github.com/microsoft/winappCli/releases/tag/v0.7.1) 显示 10 月 1 日；main 文档不等于该发行包或用户当前安装版已经具备所有命令。本轮未安装 CLI、注册身份、生成证书或修改项目。

### P2 — Quiver Launcher：升级路径也是数据生命周期

项目提供 GitHub/GitLab Release 应用库管理，官方资料包含 Avalonia 界面与测试路径；[v3.5.1](https://github.com/tgeorgiadis/quiver-launcher/releases/tag/v3.5.1) 发布页显示 10 月 15 日，不是今日发布。

更值得借鉴的是 [3.0 迁移说明](https://github.com/tgeorgiadis/quiver-launcher/blob/main/MIGRATING.md)：旧版自更新不能直接完成这次迁移，需要把应用库、设置与应用目录保留到新布局；Windows 的可替换程序目录与用户库分开。对桌面工程，这是升级前后验证数据归属的样本，不是 Avalonia 性能优于其他 UI 框架的证据。本轮未下载或运行其安装/迁移程序。

### P2 — Orca：执行主机和控制入口继续分离

[官方仓库](https://github.com/stablyai/orca) 提供桌面版本、移动伴随入口与配对 relay 的说明。对 [[AxisAgent]]，可继续观察“一个执行上下文由多个入口观察和控制”的产品模式；远程控制仍须核对主机身份、工作区和权限。仅有界面与配对功能声明，不足以认定跨端恢复或隔离已通过验证。

## 长期判断

1. **区分确定拒绝和写入不确定。** 能否重试取决于是否可能产生副作用；必要时先重新读取现场状态。
2. **把 API 可用性绑定到项目引用。** SDK 存在、符号存在、成员可写和运行时支持是不同问题。
3. **升级不能混淆程序与用户数据。** 迁移过程需要明确来源、目标、保留内容和验证结果。
