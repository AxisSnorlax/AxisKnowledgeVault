## P1 — Transub Player：按流水线阶段确认设备

[README](https://github.com/dlsandy/Transub-Player) 描述 WPF 界面、mpv 播放、Whisper 识别及 llama-server／Hy-MT 翻译的组合；模型按需下载，安装版与便携版的数据位置不同。预先准备好模型和内容后的离线使用，不意味着首次使用无需网络。

[v1.8.0](https://github.com/dlsandy/Transub-Player/releases/tag/v1.8.0) 页面显示 11 月 18 日，新增识别 GPU 选择，并区分原文识别进度与译文追赶状态。针对 Intel Arc 与 NVIDIA 双显卡及 HandBrake QSV 并发的场景，发布说明记录了识别设备选择与 CPU 线程限制调整。

[Issue #19](https://github.com/dlsandy/Transub-Player/issues/19) 中，报告者在 Arc A380／RTX 5060 的具体环境下反馈：切换播放硬解未消除识别阶段的故障，更新到 1.7.2 后同场景不再崩溃，但仍报告较高 CPU 占用。这里是外部用户的单环境反馈，既不是本轮独立复测，也不证明所有驱动或双显卡组合都已解决。

Windows/.NET 借鉴：分别记录播放、ASR、翻译的实际后端和设备，连同其他并发任务、线程限制及回退原因一起观察。流畅播放、原文进度和译文可用性应分开评价。新增判断写入 [[Local-AI]]，没有更换现有推理引擎或加载模型。

## P2 — Superpowers：工具来源目录与目标仓库分开

[v7.0.2](https://github.com/obra/superpowers/releases/tag/v7.0.2) 页面显示 11 月 3 日，是本轮复核的既有版本。其修复包含 Windows PowerShell 的 hook 命令形式、从当前工作仓库运行 helper，以及明确的 `-C` 目标；非 Git 仓库场景会停止，避免把工作文件写入插件缓存。Windows 输出路径也调整为 PowerShell 可识别形式。

同版还修复任务 ID 的歧义匹配和未闭合代码围栏导致的任务范围扩大。工程推论：脚本自身位置、目标仓库、任务身份与解析完整性都是执行前置条件；从 Skill 目录启动并不代表该目录就是工作目标。发布说明中的行为评测属于作者自报，本轮只核对文档，不采用外部 Skill 的执行指令。

## P3 — Unity MCP：空闲快照不能证明本次编译已完成

[CoplayDev/unity-mcp v10.3.0](https://github.com/CoplayDev/unity-mcp/releases/tag/v10.3.0) 页面显示 10 月 4 日，收录 [#1347](https://github.com/CoplayDev/unity-mcp/pull/1347) 的编译等待修复。该 PR 描述了编译请求入队后尚未开始，编辑器仍短暂报告 idle 的竞态，以及域重载清空静态进度字段的问题；修复采用编译事件和可跨该次重载保留的会话状态。

对 [[AxisAgent]] 的推论：请求已受理、实际开始、结束和成功结果分别取证，并关联本次操作；开始前或重载后的 idle 不能单独作为成功证明。这属于 [[Agent Verification and Audit Plane]] 的既有证据要求。该项目与 IvanMurzak/Unity-MCP 是不同仓库，不混用版本号；本轮未启动 Unity 或运行 .NET 测试。

## 本地 AI — Jan 的浏览器来源与执行权限

[Jan v0.8.8](https://github.com/janhq/jan/releases/tag/v0.8.8) 页面显示 10 月 28 日。它对浏览器调用本地 API 的 origin 做 Trusted Hosts 检查，同时保留服务端 MCP 执行的独立 opt-in 开关。无浏览器 origin 的 SDK／脚本请求仍按原有路径处理，因此来源检查不能描述成所有客户端的统一身份认证。

Windows 相关修复包括非英文用户名下的本地模型加载，以及使用系统目录中的系统工具。启用 HTTP 代理时，访问自身引擎的请求改走直连，远端 provider 仍使用代理。工程推论：本地路由、远端路由、浏览器来源和工具执行授权分别记录；不能从“本地 API 已可调用”推导“工具执行已获准”。沿用 [[Agent Capability Policy Enforcement]]，不重复追加。

## WinUI — Tiny11 Builder 的工作流状态

[winui-v0.2.0](https://github.com/ntdevlabs/tiny11builder/releases/tag/winui-v0.2.0) 页面显示 10 月 30 日。发行说明记录本地 CAB/MSU 按依赖顺序处理、暂存与 hash 检查，并让 pending servicing 状态保留在报告中；完整清单导出也不受当前界面筛选和勾选限制。

Windows 工程借鉴：界面选择集、完整库存、已执行步骤和待首次启动处理的状态应能分别查看。这里仅观察 WinUI 工具的交互与状态表达，没有生成系统镜像、移除组件或修改当前 Windows 安装；镜像构建结果仍需独立验证其启动和维护能力。
