## P1 — DBX：JSON 结果也可能已丢失数值

[DBX README](https://github.com/t8y2/dbx) 描述数据库桌面客户端、AI SQL 与 MCP 能力。[v0.6.72](https://github.com/t8y2/dbx/releases/tag/v0.6.72) 页面显示 11 月 19 日，增加只读表结构入口、按选中结果列导出 UPDATE，以及传输前计划确认。

其中 [#15153](https://github.com/t8y2/dbx/pull/15153) 明确说明：PostgreSQL 原生驱动将标量 `real` 转成 JSON 时固定保留六位小数，令 `0.0000001` 变成 `0.0`。修复使用可往返回原始 `f32` 的十进制表示；作者报告了 PostgreSQL 17.11 上的修复前后对照，本轮未独立复测。

对 Windows/.NET 专业软件的推论：原始类型与值、序列化结果、UI 格式化和写回参数分别保存及核对；格式合法不能代替数值保真。结果列选择、行身份和实际 UPDATE 范围也需单独确认，生成 SQL 不等于已执行。具体增量写入 [[Professional Software Agent Surface]]，本轮未连接或修改数据库。

## P2 — OpenSRE：有回复文本不代表执行成功

[OpenSRE 当前 README](https://github.com/Tracer-Cloud/opensre) 将项目标为 Public Alpha，描述读取失败流水线、分析日志、形成修复供审查的工作流。其嵌入式 API 示例明确：`answered` 只表示有回复文本，失败的模型调用也可能满足；该类失败另以执行状态和停止原因表达。

[v0.1.2026.11.20](https://github.com/Tracer-Cloud/opensre/releases/tag/v0.1.2026.11.20) 页面显示 11 月 20 日，但只给出相对上一版的变更范围，没有详细功能清单。固定发行页仍把 Windows 用户指向 WSL，当前主分支 README 已提供 PowerShell 安装入口，且说明默认取得 main 构建。两者不能视为同一制品的原生 Windows 支持验收。

工程推论：回复内容、模型执行、补丁产生、测试通过与目标 CI 恢复分别记录；运行状态为 completed 也不自动证明 CI 已变绿。本轮未授权候选工具操作仓库、修改 CI 或发送消息，沿用 [[Agent Verification and Audit Plane]] 的完成证据要求。

## P3 — Firecrawl：内容变化与通知送达分开

[Firecrawl v2.11.0](https://github.com/firecrawl/firecrawl/releases/tag/v2.11.0) 页面显示 6 月 19 日，是既有版本复核。它记录按站点缓存的结构化抽取器、JSON 字段级监控差异，以及按目标判断变更意义的模型步骤；同时为监控 webhook 提供尝试、投递和失败状态。

对知识监控的推论：抽取成功、字段发生变化、模型认为有意义和通知成功是不同事件。应保留来源时间、schema／抽取器身份、原始差异及投递结果；模型筛选不能抹掉无法判断的证据。本轮没有独立复现项目自报的检索指标，也没有启用外部监控或订阅。

## 本地 AI — Jan 的缓存与引擎身份

[Jan v0.8.8](https://github.com/janhq/jan/releases/tag/v0.8.8) 本轮 latest 仍返回页面显示 10 月 28 日的既有版本。其说明记录内置 llama.cpp 扩展引擎升级至 0.7.0（b11669），旧引擎保存的 prompt cache 一次性丢弃并重建；另修复附件在每轮重复追加、破坏缓存复用的问题。这里的 0.7.0 是该内置引擎版本，不将其当作所有 llama.cpp 分发统一版本号。

工程推论：缓存资格与引擎、模型及请求构成关联，升级后首次运行与稳态数据分别计时；附件在历史中的重复不能被误判为模型本身变慢。沿用 [[Local-AI]] 的版本与测量来源记录，本轮没有清理用户缓存或更换模型。
