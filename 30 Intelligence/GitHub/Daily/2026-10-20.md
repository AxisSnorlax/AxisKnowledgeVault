## 今日结论

今天值得补充的是：**压缩视图必须带有明确的原文回取条件；跨会话恢复也必须说明哪些材料仍然可访问。** Token 节省比例、能否重新取得原文和任务正确率是不同指标。

### P1 — Headroom：可回取原文不是语义无损的证明

官方 README 描述通过库、代理或 MCP 压缩工具输出，CCR 在本地保存原文并允许按需读取，但只在配置的 TTL 内保证相应回取路径。其压缩比例随内容重复程度而变，短文本和高密度内容可能收益很小。[项目资料](https://github.com/headroomlabs-ai/headroom)。

对 [[AxisAgent]] 的设计推论：压缩结果需要关联原文位置、版本、有效期与回取状态，验收和精确修改仍应读到足够的原始证据。原文已过期时应明确说明不能恢复，不能把当前摘要当作完整结果。

“20%”“60–95%”及正确率表均为项目方报告，本轮未复现。[v0.41.0 发布页](https://github.com/headroomlabs-ai/headroom/releases/tag/v0.41.0) 的发布时间栏显示 10 月 14 日，正文版本日期写为 10 月 13 日；两者都不作为今日新发布。上游另外提供会修改客户端配置或学习指令的功能，本轮没有执行。

### P1 — ai-memory：共享 Handoff 与本机历史材料分开

当前 README 描述跨 Harness 的会话衔接，同时说明：同机切换可利用本机临时历史投影，另一台机器无法读取只存在于原主机的原生会话文件。这为“可携带摘要”和“可访问原始材料”提供了具体边界样本。[README](https://github.com/akitaonrails/ai-memory)。

Windows 适配也需分层：支持矩阵仍将原生 Windows 标为 Experimental，不能因已有安装包就宣布生产资格通过。[v3.1.1 发布页](https://github.com/akitaonrails/ai-memory/releases/tag/v3.1.1) 显示 10 月 17 日，并列有 Windows 产物；本轮只核对资料，不安装、不捕获用户会话。

对 Windows/.NET Agent，Handoff 应区分可携带信息与必须在特定主机/工作区重新读取的证据。它继续属于恢复状态，不能自动晋升为已验证的长期知识。

### P2 — SMG：路由策略需要匹配实际负载

官方仓库把网关与推理引擎分开，并列出缓存感知、最小负载、固定关联等策略。[README](https://github.com/smg-project/smg)。[v1.13.0 路由文档](https://lightseek.org/smg/v1.13.0/concepts/routing/load-balancing) 进一步区分策略的状态、负载信号与适用情形；例如已固定关联的请求并不等于持续按负载重新分配。

对 [[AxisAIManager]] 的推论：先确定是否存在多 Worker、共享前缀和并发负载，再选择是否引入网关。缓存局部性、会话连续性、故障切换与访问范围不能合并成一个“智能路由”开关。现有 Provider Routing 研究继续保留，本轮不新增平行服务模型。

版本化文档与缓存的 latest 发布入口可能指向不同版本，落地时应固定发行版本逐项核对。项目“兼容 API”的声明也不能代替流式结果、工具调用、错误处理和目标 Windows 环境的验证。

## 长期判断

1. **压缩与恢复分别验收。** 压缩视图可用，不代表原文仍可取得；原文可取得，也不代表模型一定会主动回取必要信息。
2. **Handoff 明确材料的所在位置。** 本机临时材料、跨机可携带信息与长期证据需要不同的权限和保存策略。
3. **引擎、网关与 UI 分开决策。** 没有真实负载需求时不增加分布式复杂度。

本轮仅对 [[Agent Memory and Knowledge Lifecycle]] 追加原文回取条件与 Handoff 可访问范围的工作假设。已有的缓存新鲜度、证据保存及权限结论继续沿用。
