# GitHub Trending — 2026-09-29

## 今日结论

今天值得长期保留的不是一个新的通用 Agent 框架，而是 Windows/.NET Agent 工程链的进一步收敛：

1. **Windows Computer Use 正在从坐标/截图驱动转向 UI Automation / Accessibility Tree 驱动**。
2. **Agent Desktop 正在形成明确的 Windows 原生产品形态：WinUI 3 + .NET 10 + Skills/MCP + 本地持久化。**
3. **Avalonia 正出现面向 Agent/Playwright 的“可检查、可自动化、可无头测试”的 CDP Surface。**
4. **.NET 本地 AI 开始出现两条可直接工程化的路线：Microsoft Foundry Local 与 NativeAOT Local-first Runtime。**
5. **Agent Runtime 越来越强调可审计、受权限约束、可验证的 Tool Surface，而不是无限开放系统权限。**

## 值得关注

### sbroenne/mcp-windows

- 方向：Windows Computer Use / MCP / UI Automation / .NET
- 项目：https://github.com/sbroenne/mcp-windows
- 当前页面显示约 **101 stars / 17 forks**，并且 2026-09-12 连续发布到 v1.3.24。
- 核心模式：优先通过 Windows UI Automation API 按控件名称、类型和语义定位，而不是依赖固定坐标。
- 提供 UI tree、click/type、keyboard/mouse fallback、window management，并允许通过工具 allowlist/denylist 缩小暴露面。
- 对 [[AxisAgent]] 的价值：Windows 桌面自动化应优先采用 `UIA semantic action → screenshot/vision fallback`，而不是反过来。
- 进一步建议：Computer Use 工具层应加入 capability allowlist、target process/window scope、dangerous action approval 和 structured execution result。

### deploymenttheory/windows-mcp-server

- 方向：Windows MCP / Computer Use / Runtime Governance
- 项目：https://github.com/deploymenttheory/windows-mcp-server
- 当前 Star 很低（约 5），不属于热度项目，但工程方向非常值得观察。
- 除 UI Automation、PowerShell、Registry、Process、Filesystem 外，它额外强调：
  - device posture gate；
  - network egress constraint；
  - tamper-evident audit chain；
  - 每次工具调用的 policy evaluation。
- 对 [[AxisAgent]] 的意义：Tool Permission 不应只做“用户点了允许”，而应逐渐变成 **Action + Target + Device State + Network Scope + Audit Evidence** 的运行时策略。

### wieslawsoltes/CDP

- 方向：Avalonia / CDP / Playwright / MCP / Agent UI Testing
- 项目：https://github.com/wieslawsoltes/CDP
- 当前约 **55 stars / 6 forks**。
- 关键价值：为 Avalonia 应用内嵌 Chrome DevTools Protocol 风格的 inspection/automation surface。
- 支持：
  - DOM-like query；
  - evaluate；
  - screenshot；
  - tap/input/scroll；
  - Native C# MCP stdio server；
  - Playwright GUI 与 headless E2E。
- 对 [[AxisAgent]] / Avalonia 工程的价值：如果继续使用 Avalonia，可研究把 UI 可观测性和自动化能力作为正式工程 Surface，而不是只依赖截图回归。
- 这类能力尤其适合解决“Agent 很难准确修改 Avalonia UI”的长期问题：Agent 可直接读 Visual Tree、控件属性和布局结构，再做修改和回归。

### RedWoodOG/Hermes-Desktop

- 方向：WinUI 3 / .NET 10 / Windows-native Agent Desktop
- 项目：https://github.com/RedWoodOG/Hermes-Desktop
- 当前仓库约 215 commits，README 显示 v2.5.9；技术栈为 **.NET 10 / C# / WinUI 3 / Windows App SDK / SQLite FTS5 / Playwright**。
- 明确支持：
  - portable self-contained Windows build；
  - provider switching；
  - MCP host；
  - Skills；
  - memory / transcripts / wiki；
  - WinUI 原生桌面。
- 对 [[AxisAgent]] 的价值：这是一个比通用 Sample 更接近目标产品形态的参考项目。
- 重点应研究架构与工程组织，而不是复制 UI：Provider、Skill、Memory、MCP、Session、Portable Packaging、真实 Smoke/Test 如何解耦。

### Retro-Downfall/RetroDownfall.Arcanum

- 方向：.NET 10 / NativeAOT / Local-first AI Runtime
- 项目：https://github.com/Retro-Downfall/RetroDownfall.Arcanum
- 当前状态：0.1.0-beta。
- 技术组合：**.NET 10 + ASP.NET Core Minimal API + NativeAOT + Microsoft.Extensions.AI + SQLCipher + Avalonia + MCP**。
- 核心设计：
  - self-contained executable；
  - OpenAI-compatible API；
  - local encrypted store；
  - 可路由本地或远端 OpenAI-compatible provider；
  - long-lived host + thin clients。
- 对 [[AxisAIManager]] / [[AxisAgent]] 的价值：Runtime 与 UI 解耦、OpenAI-compatible façade、加密本地状态、NativeAOT CLI/Host 都很值得借鉴。
- 边界：仍是 beta，应作为架构研究候选，不应直接替换现有 Runtime。

### Microsoft Foundry Local

- 方向：Windows Local AI / C# / WinUI / WPF
- 文档：https://github.com/MicrosoftDocs/windows-ai-docs/blob/docs/docs/foundry-local/get-started.md
- Microsoft 当前文档明确支持 C#/.NET 直接运行本地模型，并可用于 WinUI 3、WPF 或其他 .NET host。
- Windows 路线使用 `Microsoft.AI.Foundry.Local.WinML`，可使用硬件加速。
- 对 [[AxisAIManager]] 的价值：Foundry Local 应加入 Windows 本地推理 Benchmark 候选，与 llama.cpp / Ollama / ONNX Runtime 路径做同机实测，而不是仅按文档判断优劣。
- 建议比较：Cold Start、TTFT、tokens/s、VRAM、RAM、模型下载/缓存、GPU/NPU 适配、API 稳定性、NativeAOT/部署兼容性。

### ramseur/sovrant

- 方向：.NET 10 Agent Runtime / Desktop / Web / MCP / Orchestration
- 项目：https://github.com/ramseur/sovrant
- 当前 README 展示的是完整 .NET Agent 平台形态：CLI、OpenAI-compatible Server、Avalonia Desktop、Blazor Web、MCP、Skills、Memory、Projects、Teams、Swarm、Mission、Cost、Eval、Permissions。
- 对 [[AxisAgent]] 的意义不在“功能越多越好”，而在于其边界划分：
  - Runtime 独立；
  - Desktop/Web/CLI 是前端；
  - Provider abstraction 独立；
  - Tool/Skill/Storage 单独分层。
- 可作为 AxisAgent 架构审计时的反例/参考样本，检查是否把 UI、Runtime、Tooling、Provider、Memory 耦合在一起。

## 今日长期判断

### 1. Windows Computer Use：UIA First

建议长期模型：

```text
Semantic UI Automation / Accessibility Tree
  ↓
Structured Target Resolution
  ↓
Action + Result + Evidence
  ↓
Screenshot / Vision Fallback
  ↓
Raw Mouse / Keyboard Last Resort
```

原因：坐标和纯视觉方案对 DPI、窗口移动、主题和布局变化更脆弱。

### 2. Tool Permission 应进入 Runtime Contract

不再只做：

```text
Allow / Deny
```

而应逐渐演化为：

```text
Tool
+ Action
+ Target
+ Process / Window Scope
+ Filesystem Scope
+ Network Scope
+ Device State
+ Approval Requirement
+ Audit Evidence
```

### 3. Desktop Agent 应按“Runtime + Surfaces”设计

```text
Agent Runtime
  ├── Provider
  ├── Tool / MCP
  ├── Skill
  ├── Memory / Knowledge
  ├── Permission
  ├── Run / Audit
  └── Routing
        ↓
Frontends
  ├── WinUI / Avalonia Desktop
  ├── CLI
  ├── Web
  └── API
```

不要让桌面 UI 成为 Runtime 本身。

### 4. UI Framework 需要“Agent 可操作性”新指标

以后评价 WinUI / Avalonia / WPF 不应只比较 FPS、内存和视觉：

- Visual Tree 是否可可靠检查；
- UI Automation 暴露质量；
- Headless/E2E 能力；
- Agent 是否能稳定定位控件；
- 是否可以程序化读取布局、样式、状态；
- UI 修改后能否自动验证。

`wieslawsoltes/CDP` 说明 Avalonia 已开始出现这种工程方向。

## 本次扫描边界

今天没有发现足以证明“WinUI 3 已经全面优于 Avalonia”或“Avalonia 应继续作为 AxisAgent 唯一桌面框架”的新证据。UI 技术选择仍应以同机 Benchmark、开发效率、视觉还原、UI Automation、长期维护成本共同决定。

同样，Foundry Local 与 Arcanum 都应先进入 Research / Benchmark 候选，不应因为新颖性直接替换现有 llama.cpp / provider runtime。
